###### 系统设计：把工具职责和数据流固定下来

> 产品设计的同时，就可以启动系统设计了，这个项目使用的工具不少，但每个工具只负责一段稳定的工作任务：WorkBuddy 负责发现列表；
>
> 飞书负责配置和队列；
>
> n8n 负责深抓和编排；
>
> Supabase 负责数据存储；
>
> CodeBuddy 负责在明确规则下生成应用代码。

**总体架构**

**涉及到的开发工具**

| 工具      | 在本项目中的任务                                             | 明确不负责的内容                            |
| :-------- | :----------------------------------------------------------- | :------------------------------------------ |
| WorkBuddy | 定时访问目标站点列表页，解析标题、链接、类型、日期、地区等字段，去重后写入飞书 | 不抓详情页，不直接写 Supabase，不做客户推送 |
| 飞书      | 维护源站配置表和公告列表队列，提供人工查看、修正和状态回写入口 | 不承担最终历史数据存储，不承担复杂查询页面  |
| n8n       | 定时通过 MCP 读取飞书待抓记录，按链接抓详情，处理验证码，结构化抽取并写 Supabase；入库后匹配订阅，调用飞书群机器人推送，并记录推送结果 | 不重新抓列表页，不替代应用页面              |
| Supabase  | 保存公告、详情、订阅和执行日志，向后端提供稳定的数据层       | 不直接访问外部招投标网站                    |
| CodeBuddy | 按需求确认单、架构文档和 Rules 生成前后端代码、接口和测试    |                                             |

**WorkBuddy 到飞书：只处理列表发现**

WorkBuddy 上网搜素抓取地方性或全国性的招投标信息的网站格式化写入到飞书当中。

每次任务只做列表页发现：读取启用的站点配置，抓取列表页，解析公告标题、详情链接、公告类型、发布日期、地区和来源站点，按详情链接查重后写入飞书“招标列表表”，状态统一设为“待抓取”。

列表阶段不追求把详情字段全部补齐，因为不同网站详情页结构差异很大，预算、联系人、截止时间等字段留给 n8n 深抓阶段处理。这样 WorkBuddy 的任务足够简单，也不会因为某个详情页的验证码或异构结构拖慢列表发现。

>
> 站点等级
>
> 最近抓取时间
>
> 列表页URL

>

> 备注

**n8n 到 Supabase：通过链接深抓详情**

n8n 由定时触发器启动，通过 MCP 读取飞书中“抓取状态=待抓取”的记录，按批次取出详情链接。它根据链接所属站点选择解析方式：静态 HTML 直接解析；需要浏览器渲染的站点用浏览器节点打开；触发简单验证码时，进入验证码子流程识别并重试。

验证码通过后，n8n 从详情页抽取标题、采购人、地区、预算金额、报名或截止时间、联系人、联系电话、代理机构和正文摘要等字段，写入 Supabase。

写入成功后回写飞书“已入库”，再进入推送子流程：读取启用的订阅，按关键词、地区和公告类型匹配，调用飞书群机器人发送公告摘要和原文链接，并把每一个订阅的发送结果写入 `bid_push_log`。



**推送设计：入库后同步发送到飞书群**

推送是这套系统真正产生业务价值的一步。前面的采集和入库解决“信息能不能找到”，推送解决“客户能不能及时收到”，因此推送不能作为应用页面上的附属按钮，而要作为 n8n 深抓流程成功后的一个自动子流程。

**推送需求**

| 需求项   | 任务约定                                                     |
| :------- | :----------------------------------------------------------- |
| 触发时机 | 公告详情成功写入 Supabase 后触发，不等人工点击               |
| 匹配条件 | 订阅启用状态 + 关键词 + 地区 + 公告类型；空条件表示不限制该项 |
| 推送对象 | 订阅记录中配置的飞书群机器人 Webhook                         |
| 推送内容 | 标题、公告类型、地区、采购人、预算金额、截止时间、来源站点、原文链接 |
| 推送形式 | 首期使用飞书机器人文本或卡片消息，格式固定，便于统一维护     |
| 重复控制 | `announce_id + subscription_id` 作为推送幂等依据，同一订阅不重复发送 |
| 失败处理 | 记录 HTTP 状态码和错误信息，有限重试；仍失败显示为待重试，不影响公告入库 |
| 人工处理 | 机器人地址失效、权限不足或连续失败时，在推送记录页面提示人工处理 |

推送内容示例

```Plain
【招投标信息提醒】
公告标题：某工程项目公开招标公告
公告类型：招标公告
地区：江苏省南京市
采购人：某某建设单位
预算金额：¥1,280,000
报名/截止时间：2026-09-20 17:00
来源站点：中国政府采购网
查看原文：https://example.com/detail/123
```

**n8n 推送子流程**

子流程里有一个必须坚持的顺序：先写入 Supabase，再发送机器人消息，最后记录推送结果，如果先发消息、后写数据库，网络抖动时可能出现客户已经收到公告、系统却没有记录的情况；如果推送失败，也不能把已经保存的公告删掉，只需要按推送日志重试。



**Supabase 数据设计**

为了实操方便，本次使用Supabase 作为数据库存储，Supabase 使用的是 PostgreSQL 作为最终存储，n8n只做写入、而应用只读取这里的数据，也不需要复杂的数据仓库，这里就设计了五张核心表：

| 表                 | 用途                 | 关键字段                                                     |
| :----------------- | :------------------- | :----------------------------------------------------------- |
| `bid_announce`     | 公告主记录           | `title`、`detail_url`、`announce_type`、`publish_date`、`purchaser`、`region`、`source_site`、`budget`、`crawl_status` |
| `bid_detail`       | 详情正文和结构化字段 | `announce_id`、`content_html`、`content_text`、`structured`、`crawled_at` |
| `bid_subscription` | 客户订阅条件         | `keyword`、`region`、`announce_type`、`channel`、`webhook_url`、`enabled` |
| `bid_crawl_log`    | 抓取和运行日志       | `run_at`、`total`、`success`、`failed`、`manual`、`note`     |
| `bid_push_log`     | 推送结果             | `subscription_id`、`announce_id`、`channel`、`status`、`sent_at`、`error_message` |

`detail_url` 是全链路唯一键，列表写入、详情 upsert 和应用查询都以它作为去重基础。公告正文可以保留原文快照，结构化字段放在 JSONB 中，便于不同站点的字段存在差异时先落库，后续再逐步完善解析规则。

严格按照数据库脚本进行设计。



**CodeBuddy 的 AI 规约编程规则**

前后端采用适合本项目 MVP 的 Node.js 全栈技术栈：Next.js + TypeScript，页面使用 React 和 shadcn/ui，数据访问使用 Supabase SDK，表单和参数校验使用 Zod。CodeBuddy 不直接从聊天记录生成代码，而是先读取项目根目录中的规则和设计文件：

```Plain
项目根目录/
├─ .codebuddy
│  ├─ rules                  # 项目rules
│  └─ skills                 # 项目技能
├─ openspec
├─ CODEBUDDY.md                 # 技术栈、目录、分层和禁止事项
├─ docs/
│  ├─ requirements.md        # 需求确认单和 MVP 边界
│  ├─ product-design.md      # 5 个页面、字段和交互
│  ├─ architecture.md        # 本章系统设计
│  └─ api-contract.md        # 接口路径、入参和出参
├─ application/
│  ├─ app/                 # Next.js 页面与路由
│  │  └─ api/              # Route Handlers 服务端接口
│  ├─ components/          # 可复用页面组件

│  ├─ types/               # 公告、订阅和推送日志类型

```

Rules 至少固定五件事（我现在已经有一套通用Rules，你下面有重复的就不要创建）：

1. 技术栈和版本，防止 AI 随意引入新的框架或依赖；
2. Next.js 页面、服务端接口、组件目录、命名方式和接口返回格式；
3. 分层边界，例如页面组件不直接操作高权限数据库连接，业务访问统一经过服务端函数或 API Route；
4. 业务术语和数据库字段的对应关系，例如“公告详情链接”统一使用 `detail_url`；
5. 禁止事项，例如不允许前端直接访问 Supabase 密钥、不允许应用绕过后端抓外部网站、不允许 AI 自动把“待人工”改成“已入库”。

CodeBuddy 的开发顺序也固定下来：先根据四个页面和数据库表输出 REST 接口契约，再生成 TypeScript 类型、服务端接口、数据访问函数和页面组件；每完成一个模块，先执行类型检查、构建和对应测试，再进入下一个模块。



首期接口至少包括：

| 接口                          | 用途                                                 |
| :---------------------------- | :--------------------------------------------------- |
| `GET /api/announces`          | 分页查询公告，支持关键词、地区、类型、时间和来源筛选 |
| `GET /api/announces/{id}`     | 查看公告结构化字段和正文摘要                         |
| `GET /api/subscriptions`      | 查询当前订阅                                         |
| `POST /api/subscriptions`     | 新增订阅                                             |
| `PUT /api/subscriptions/{id}` | 修改或停用订阅                                       |
| `GET /api/push-logs`          | 查看推送结果和失败原因                               |

新增接口：GET /api/crawl-logs   



开发阶段可以使用数据库只读连接或 Supabase 的受限凭据让 CodeBuddy 查看表结构；

这样 AI 负责生成重复性代码，FDE 仍然负责需求判断、边界控制和最终放行。
